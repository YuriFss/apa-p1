Ordenação em tempo linear: limite inferior e CountingSort

Os 28 slides da Aula 8. Primeiro, por que nenhum algoritmo baseado em comparações vence $n\log n$. Depois, como o CountingSort escapa disso: ele não compara elementos, conta.

1. O que vimos até agora

InsertionSort, SelectionSort, MergeSort e QuickSort: todos baseados em comparações ($A[i] < A[j]$?). Os melhores têm pior caso $O(n\log n)$. Existe algo assintoticamente melhor que $O(n\log n)$? Não, se o algoritmo for baseado em comparações!

2. Limite inferior $\Omega(n\log n)$: árvore de decisão

Qualquer algoritmo baseado em comparações é, no fundo, uma árvore de decisão binária: cada nó interno é uma comparação, com dois ramos (sim/não), e cada folha é uma ordem final. Exemplo do slide, para 3 elementos $a_1, a_2, a_3$:

Folha "2 1 3" quer dizer: a ordem crescente é $a_2, a_1, a_3$. Ramo da esquerda = "não", da direita = "sim".

  1. Qual o número de comparações no pior caso? É o caminho mais longo da raiz até uma folha: a altura $h$ da árvore. Aqui, $h = 3$.
  2. Quantas folhas a árvore precisa ter? Cada resultado possível do vetor é uma folha. Os resultados são as permutações dos $n$ elementos: pelo menos $n!$ folhas. Com 3 elementos, $3! = 6$ folhas, como na figura.
  3. Uma árvore binária de altura $h$ tem no máximo $2^h$ folhas. Cada nível dobra o número máximo de nós.
  4. Juntando: $2^h \ge n! \;\Rightarrow\; h \ge \log n!$.
  5. É conhecido que $\log n! \ge c\,n\log n$ para alguma constante $c > 0$.
Conclusão (slide 9)

Todo algoritmo de ordenação baseado em comparações faz pelo menos $\Omega(n\log n)$ comparações no pior caso. MergeSort já atinge isso, então é assintoticamente ótimo entre os algoritmos por comparação.

Por que $\log n! \ge c\,n\log n$? (fora dos slides)

Metade dos fatores de $n! = 1\cdot2\cdots n$ são $\ge n/2$, então $n! \ge (n/2)^{n/2}$. Aplicando log: $\log n! \ge \frac{n}{2}\log\frac{n}{2} = \frac{n}{2}(\log n - 1)$, que é $\ge \frac{1}{4}n\log n$ para $n \ge 4$. Logo vale com $c = 1/4$.

3. Algoritmos que não comparam

Existem algoritmos de ordenação que não são baseados em comparação: CountingSort, RadixSort e BucketSort. O limite $\Omega(n\log n)$ não vale para eles. Mas como ordenar um vetor sem comparar seus elementos? A disciplina estuda o CountingSort.

4. CountingSort: ideia e os três vetores

Pressupõe que cada um dos $n$ elementos de entrada é um inteiro no intervalo de 0 a $k$, para algum inteiro $k$.

Ideia básica (slide 16)

Determinar, para cada elemento de entrada $x$, o número de elementos menores que $x$. Com essa informação, dá para colocar o elemento diretamente na sua posição no vetor de saída. Exemplo: se houver 17 elementos menores que $x$, $x$ vai na posição 18.

Usa 3 vetores:

  • A[0..n−1]: vetor de entrada, desordenado;
  • B[0..n−1]: vetor de saída, ordenado;
  • C[0..k]: vetor auxiliar de contagem, uma posição para cada valor possível.
Cuidado com o $k$ do slide 15

No exemplo com valores em $[0, 9]$, o slide escreve "$k = 10$", contando quantos valores existem. No pseudocódigo, $k$ é o maior valor ($C[0..k]$), então ali seria $k = 9$. Na prova, deixe claro qual dos dois você usa. A complexidade $O(n + k)$ não muda.

5. Pseudocódigo, linha a linha

CountingSort(A, B, k, n)
1.   for i ← 0 to k do
2.      C[i] ← 0
4.   for j ← 0 to n − 1 do
5.      C[A[j]] ← C[A[j]] + 1
7.   for i ← 1 to k do
8.      C[i] ← C[i] + C[i − 1]
10.  for j ← n − 1 downto 0 do
11.     B[C[A[j]] − 1] ← A[j]
12.     C[A[j]] ← C[A[j]] − 1
FaseLinhasDepois dela, $C[v]$ guarda…
1. Zerar1–2$0$
2. Contar4–5quantas vezes o valor $v$ aparece em $A$
3. Acumular7–8quantos elementos são $\le v$ (soma de prefixos)
4. Posicionar10–12a próxima posição livre (+1) para o valor $v$ em $B$

Por que a linha 11 usa $C[A[j]] - 1$? Depois da fase 3, $C[v]$ é a quantidade de elementos $\le v$. O último $v$ deve ocupar essa posição contando a partir de 1. Como $B$ começa em 0, subtrai 1. A linha 12 decrementa $C[v]$, e o próximo $v$ (mais à esquerda em $A$) vai uma casa antes.

As legendas das figuras do slide falam em "linhas 3 e 4", "6 e 7" e "9, 10 e 11": é uma numeração antiga, uma linha antes da do pseudocódigo. Elas correspondem às fases 2, 3 e 4 da tabela.

6. Animação (exemplo do slide)

CountingSort em A = [2, 5, 3, 0, 2, 3, 0, 3], k = 5

A linha "origem" abaixo de B mostra de qual índice de A veio cada elemento: os iguais saem na mesma ordem relativa da entrada (estabilidade). Confira os estados do slide: depois da fase 2, C = [2, 0, 2, 3, 0, 1]; depois da fase 3, C = [2, 2, 4, 7, 7, 8].

7. Complexidade: $O(n + k)$

LaçoIteraçõesTempo
linhas 1–2$k + 1$$O(k)$
linhas 4–5$n$$O(n)$
linhas 7–8$k$$O(k)$
linhas 10–12$n$$O(n)$

São laços em sequência, não aninhados, então os tempos se somam: $O(k) + O(n) + O(k) + O(n) = O(n + k)$. Ou seja, pseudolinear: linear em $n$ e em $k$.

Na prática usamos $k = O(n)$, quando o maior valor não é muito maior que a quantidade de elementos, e o tempo total vira $O(n)$.

Quando não compensa

Se $k$ for enorme perto de $n$ (ex.: 10 números entre 0 e $10^9$), o vetor $C$ tem $10^9$ posições: $O(n + k)$ fica muito pior que $O(n\log n)$. O CountingSort só vale a pena para inteiros num intervalo pequeno.

8. Estabilidade

Slide 28

O CountingSort é um algoritmo estável: se o vetor tiver elementos iguais, eles aparecem na mesma ordem no vetor ordenado. Dependendo da aplicação, isso pode ser essencial. MergeSort e InsertionSort também são estáveis.

O que garante a estabilidade é a fase 4 percorrer $A$ de trás para frente (downto): o último $3$ de $A$ ocupa a última posição de $3$ em $B$, o penúltimo fica antes dele, e assim por diante. Use o botão "downto trocado por to" na animação para ver os iguais saírem invertidos.

Exemplo de por que importa: ordenar uma planilha de alunos por nota mantendo, entre notas iguais, a ordem alfabética que já existia. O RadixSort depende disso para funcionar.
